# LeebertyPV

**让日常药物警戒（PV）义务可执行、可追溯、可审计。**

一个面向中国药品上市许可持有人（MAH）、医疗机构与药物警戒部门的本
地化合规工作台。覆盖**个例安全性报告（ICSR）、信号检测与评估（SIGNAL）、
定期安全性报告（PSUR/PBRER）、风险管理（RMP）、医学文献监测（LIT）、
疫苗疑似预防接种异常反应（AEFI）、药品投诉与召回（COMPLAINT）与药物警戒
体系质量合规（GVP）** 八大领域，把"文件规定应该怎么做"变成"系统推着你做、
做错拦住、做完自动留痕"，并在检查前就告诉你哪里有风险。

本产品由 LeebertyGXP 架构改造而来：合规内核（哈希链审计、双要素电子签名、
职责分离）与"领域是数据"的设计原封保留，领域集合整体替换为治疗性药物警戒。
**这不再是 GMP/GLP/GCP 工作台** —— 设备校准、批次放行与 GxP 生产领域已不在
本产品的范畴内。

## 一、为什么这样设计

市面上多数"药物警戒软件"是电子档案柜：把纸质表格搬进数据库，录入员照样填错
时限、QA 照样在检查前突击补记录。这样的工具不解决真问题，反而制造新的数据
完整性与合规风险。

本工作台基于四个判断：

**1. PV 各领域的合规义务高度同构。**
快速报告、信号评估、PSUR 编制、RMP 更新、文献筛查、偏差/CAPA——本质都是
"一条受控的安全性记录 + 一串有角色与签名门槛的步骤"。所以不能一个领域写一套
代码。**领域是数据，不是代码**：加一个新流程只需往 `seed/workflows/` 放一个 JSON
文件，加一张检查表只需往 `seed/checklists/` 放一个 JSON 文件。

**2. 合规控制必须做进机制，不能靠自觉。**
审计追踪用哈希链实现，改库会被触发器拦死，绕过触发器改文件会被摘要校验抓出；
电子签名强制两个独立识别要素；所有安全性记录修改强制填写理由；因果评价的录入员
不能自评，偏差的提出人不能自己关闭。这些是**代码强制**的，不是制度要求。

**3. 检查就绪度必须常态可见，而非临时突击。**
系统把法规条款变成可判定的检查项，把自检发现的每一项缺陷一键转成受控 CAPA，
并把未关闭缺陷、报告超期、文件审核欠账、培训过期、审计链完整性汇成一个就绪度
评分，直接列出**具体阻碍项**。

**4. 工作流要自己跑，不能等人来查。**
报告时限、随访任务、CAPA 有效性检查、培训到期——所有催办逻辑如果只在"打开
页面时计算"，系统就是被动的。所以有一个后台进程常驻，定时扫描超期记录、待签
步骤与过期资质，生成待办、升级严重超期、并在条件解除后自动关闭——**不需要
任何人打开页面**。

### 各领域的设计理念（`src/domain/explorer.js` 的 PHILOSOPHY 常量，一行一句）

| 领域 | 理念 |
|---|---|
| **ICSR** | 时限不是目标，而是底线。报告时钟从你首次获知四要素的那一天开始计算，而不是从病例"做完"那天开始。 |
| **SIGNAL** | 信号管理是获益-风险评估的引擎：个例报告是原料，比例失衡是线索，医学判断才是结论。 |
| **PSUR** | 定期报告不是年度总结，而是对累积证据的获益-风险评估——数据锁定点决定它覆盖什么、何时提交。 |
| **RMP** | 风险管理的价值不在写出一份计划，而在把风险最小化措施做进日常工作并验证它们真的有用。 |
| **LIT** | 文献里的一句话可能就是一个待上报的个例。检索不能停，筛查必须有记录，转交必须有时限。 |
| **AEFI** | 疫苗安全的第一课是分类：一般反应与异常反应的区别，决定了报告时限与公众沟通的方式。 |
| **COMPLAINT** | 投诉里可能藏着未报告的不良反应。先判断是否涉及安全性，再处理质量本身。 |
| **GVP** | 质量体系不是文档堆，而是把偏差、CAPA、变更、内审、培训变成可执行、可追溯、可审计的日常。 |

这些理念不是悬浮提示，而是领域卡、领域页、工作流页反复出现的一行字，可以被
截图、打印、贴到办公室墙上。

## 二、快速开始

### 只要双击一次

```
双击  LeebertyPV.exe     （或 双击 start.bat）
```

**首次启动会自动完成全部初始化**，不需要先跑任何脚本：

1. 创建数据库（`data/pv.db`）、生成审计链密钥（`data/audit-chain.key`）
2. 加载配置库（12 类 PV 流程定义 + 领域登记表；`seed/` 目录）
3. 创建演示账号（**26 个身份**：13 个内置演示身份 + 演示数据集再创建 13 个场景账号，统一密码 `PV-Demo-2026!`）
4. **库中没有任何安全性记录时自动生成演示数据集**（虚构记录，见第八节）
5. 校验审计链完整性 —— 通过
6. 启动后台工作流进程（默认每 5 分钟扫描一次）

全流程通常是几秒钟，然后打开**身份选择页**。第二次启动发现数据已存在，只
重载配置库，不重复生成。

托盘出现蓝黑底色的 **PV** 图标，工作台在**它自己的原生应用窗口**中打开（WinForms
窗口：自己的标题栏、任务栏图标；**不使用 Edge / WebView2 / 任何浏览器组件**）。
托盘菜单可以：打开工作台、生成演示数据、校验审计追踪、备份数据、停止并退出。

这个 exe 是**单文件、零第三方依赖**，由 Windows 自带的 C# 编译器（.NET Framework
的 `csc.exe`）现场编译——窗口用原生 WinForms 控件渲染，数据通过本地 REST API
读取自同机运行的 Node 服务。

<details>
<summary>为什么不是「先跑生成演示数据.bat，再跑 exe」</summary>

早期版本需要两次双击，而且桌面快捷方式上完全看不出第一步的存在。现在初始化
并入服务启动过程（`src/bootstrap.js`），因为**第一次打开时的体验就是产品本身**。

演示数据集的自动生成**受内置账号开关约束**：它写入的是虚构的个例、信号与签名，
进入真实审计追踪。生产实例绝不能发现里面有编造记录，所以
`PV_BUILTIN_ACCOUNTS` 未开启时既没有虚构账号，也不会生成演示数据。
</details>

### 方式二：批处理启动

```
双击  start.bat
```

行为与 exe 相同，区别是**带控制台窗口能看到日志**（排查问题时用这个）。

- `start.bat` — 带控制台窗口，默认端口 **8793**（`start.bat 9000` 换端口）
- `start-silent.bat` — 后台静默启动，日志写入 `logs/server.log`
- `stop.bat` — 停止后台实例（按端口定位进程并停止）
- `生成演示数据.bat` — 手工重新生成演示数据（通常不需要，首次启动已自动完成）

### 打开后你会看到什么

**程序自己的原生应用窗口，不是浏览器页面** —— 双击 `LeebertyPV.exe`（或 `start.bat`），
会打开**原生 WinForms 应用窗口**：自己的标题栏、任务栏图标与托盘菜单，界面全部用
Windows 原生控件绘制（领域卡片、流程图、权限矩阵、待办列表、记录表单、电子签名
对话框等），通过本地 REST API 与同机的 Node 服务通信，**不依赖 Edge / WebView2 /
任何浏览器组件**。Web 界面仍作为可选访问方式保留（`http://127.0.0.1:8793`）。

**第一屏是身份选择** —— 打开后先回答"你是谁"。身份按**职责范围**分三组：

| 分组 | 谁 | 登录后去哪 |
|---|---|---|
| **全域职责** | 药物警戒质量负责人、内审员、培训协调员、监管检查员（只读）、系统管理员 | 进入**领域选择**（他们的职责横跨全部领域，需要先决定看哪个） |
| **各领域专职** | 数据录入员、药物警戒专员、医学评价员、QPPV、报告撰写员、报送专员、文献监测员、药品安全委员会委员 | **直接进入该身份的专属领域界面** |
| **其他身份** | 只读访客等 | 进入领域选择 |

**流程：选领域 → 选身份 → 进入领域专属界面。** 每张身份卡上写明它属于哪个
领域（"进入 ICSR"、"进入领域选择"），所以选择是有依据的。密码是**真的校验**
的：输错会明确提示"密码不正确"，而不是放行。

> **为什么共用一个密码却仍然要求输入？** 演示账号共用同一密码是**已标注的风险**
> （见第四、八节，21 CFR Part 11.300(a) 要求账号唯一）。但"点一下就进去"展示的
> 是**去掉认证之后的授权**，而且一个可以跳过的认证步骤会教给读者"它是可选的"。
> 所以弹窗里给出演示口令作为提示，但**必须键入**才能进入。

**登录后：领域优先，一卡见流程图。** 领域卡片在最前，点任意领域卡（如 ICSR），
**第一屏就是该领域的工作流程图**：横向步骤、每步下方是责任人名片（姓名·职务·
职责）、名片下方是他在这个岗位实际持有的各项权限——这正是把"流程图看不见"的
根因修掉后的样子。

**「领域与流程」页的顶上就是流程图。** 侧边栏点"领域与流程"，打开后第一块就是
一行领域胶囊（ICSR / SIGNAL / PSUR / RMP / LIT / AEFI / COMPLAINT / GVP），下面是
当前所选领域的流程图级联，点胶囊即时切换，整个过程**无需登录**（流程图是参考
模型，对所有人公开）。

**领域专属界面** —— 一个界面看全该领域：工作流程与责任分工（横向步骤，每步
下面是负责人名片，名片下面是他的各项权限）→ 流程清单 → 岗位职责 → 信息权限
对应表 → 覆盖本领域的法规自查表。超出你职责范围的岗位名片会**灰显**，点击后
说明拒绝理由。

**选择身份后看到的才是「我的待办」** —— 列出等待该身份提交/批复/核实/执行的
条目，按后果轻重排序（不是按时间），并明确标出哪些需要电子签名、哪些已经超期
几天。底部还有一块"你的权限范围"，说明这个岗位**不能**做什么。

**新增用户（`系统管理员` 身份 → 用户与权限 → 新增用户）。** 只有系统管理员能
建账号（`user.manage`）。弹窗里除姓名/角色/部门外，还可以**声明该人员所属的
PV 领域**：声明后账号会出现在该领域的身份名单里，登录落点也按本人声明优先。
初始密码可留空（之后用「重置密码」签发临时密码），可勾选"首次登录必须修改密码"。

不想要内置账号？用 `PV_BUILTIN_ACCOUNTS=0` 启动，就会回到"创建第一个管理员
账号"的标准流程，同时**不会生成演示数据**。

### 环境要求

**只需要 Node.js 22.5 或更高版本**（依赖内置的 `node:sqlite`）。
**零第三方依赖** —— 不需要 `npm install`，断网可运行。
桌面启动器额外需要 Windows 自带的 .NET Framework C# 编译器（构建时）与
Edge / WebView2（运行时）。

这不是技术洁癖，而是合规优势：在受验证环境里，每一个第三方包都需要单独的
供应商评估与变更控制（EU GVP Module I 质量体系 / Annex 11 §7.1 的精神）。
零依赖意味着供应商评估范围极小。

## 三、核心能力

### 报告时限引擎（`src/domain/deadline.js`）

药物警戒里最容易"看起来没问题、其实已经违规"的地方，就是报告时限的起算点。
所以时限不是一个人手填的日期，而是由系统按法规算出、并且**能解释自己怎么算的**
一条规则。

| 规则 | 时限 | 依据 |
|---|---|---|
| 严重不良反应 | 获知后 15 日 | GVP 第四十九条 |
| 非严重不良反应 | 获知后 30 日 | GVP 第四十九条 |
| 死亡病例 | 立即报告；调查报告 15 日内 | GVP 第四十九条；《药品不良反应报告和监测管理办法》第十二条 |
| 境外暂停销售/使用/撤市 | 获知后 **24 小时** | GVP 第五十一条 |
| 跟踪报告 | 按首次报告的时限，**自新信息获知日重新起算** | GVP 第四十九条 |

**起算日（Day 0）= 持有人首次获知该个例、且四要素（可识别患者 / 可识别报告者 /
怀疑药品 / 不良反应）齐备之日**（GVP 第四十六条、第四十九条，ICH E2D）。两个条件
必须同时满足；缺任一条时钟就未起算，并同时提示"缺失要素须立即随访"。

这带来三个具体行为：

- **病例补录不会洗掉时钟。** 一张在邮箱里躺了十天没人登记的报告，登记当天即已
  消耗 10 天，系统不会因为"今天新建"而重新给 15 天。
- **分诊会改变时限。** 非严重病例初判 30 日；分诊判定为严重后，时限自动收紧为
  15 日，且这次变更连同依据一起写入审计追踪。
- **严重性未判定时从严起算。** 严重性未判定按 15 日计算并标注"从严起算"，
  而不是默认给 30 日——把可能严重病例误判为非严重的代价不可逆。

界面上，病历详情页顶部固定显示**时限面板**：截止日、剩余/超期天数、起算日与起算
依据、所适用的规则与法规条款。剩余天数用文字写明（"剩余 6 天"/"已超期 3 天"），
颜色只做辅助——该页面要能被打印成黑白证据页。

> **为什么必须做。** 旧实现用 `Date.now() + slaDays` 计算截止日，即"录入当天 +
   SLA"。这不会报错、界面完全正常，但审计追踪会把已经超期的报告记成合规。而
   待办排序、超期任务、就绪度评分全部读 `due_date`，一处错误会污染全部四个界面。

### MedDRA 编码（`src/domain/coding.js` + `seed/dictionaries/`）

不良反应术语不再是一段自由文本。自由文本看着无害，实际是致命的：「肝损伤」「肝损害」
「ALT 升高」「drug induced liver injury」在 MedDRA 里是**同一个 PT**，存成四个
字符串就无法汇入定期报告例数、无法做比例失衡分析——因为信号是"已编码的药品-事件
配对"的属性，没有配对就没有信号。

- 编码结果同时保存 **PT 与 SOC**，汇总是分组而不是字符串匹配
- 支持中文 LLT、英文 PT 名、PT 编码三种输入
- **未命中词典的术语不会被静默接受**，而是标记为"未编码"并提示：未编码数据会
  使定期报告例数偏低，须由授权编码员补齐词典或改选术语
- 内置 SMQ（标准化 MedDRA 查询），可按查询展开成员 PT 做群组分析
- 随包词典为**本地常用术语子集**（`LeebertyPV-MedDRA-subset-2026.1`，11 个 SOC /
  58 个 PT）。正式注册申报须使用经许可的完整 MedDRA 版本——README 与接口响应
  都明确标注了这一点，不让演示词典被误当成申报词典

### 信号检测（`src/domain/signal.js`）

GVP 第五十六条要求持有人选择适当、科学、有效的信号检测方法，并明确把数据挖掘
列为可选方法之一。这就是那个方法，跑在本实例真实持有的病例上。

| 统计量 | 方法 | 判定标准 |
|---|---|---|
| PRR | Evans 准则 | PRR ≥ 2 **且** χ² ≥ 4 **且** 例数 ≥ 3 |
| ROR | 频率学派 | 95% CI 下限 > 1 |
| IC025 | BCPNN（WHO-UMC / VigiBase 方法） | 95% 可信区间下限 > 0 |
| EB05 | MGPS（FDA FAERS 方法） | 单侧 90% 区间下限 > 1 |

设计上的三个关键点：

1. **按病例计数，不是按配对实例计数。** 2×2 表的四个格子是病例数，所以同一
   药品-反应组合的 8 张病例是一个 `a = 8` 的配对，不是 8 个 `a = 1` 的配对。
   这一条错了，所有统计量都失去意义。
2. **必须收缩统计与频数统计一致才触发。** 3 张报告就能算出惊人的 ROR；IC/EBGM
   正是用来把它拉回原点的。反过来，PRR 达标而 IC025 为负的组合**不会**被报为
   信号——测试里专门钉住了这条。
3. **无对照时如实说明"不可计算"。** 某药品只报告过一种不良反应、或没有其他药品
   报告同一术语时，PRR/ROR 数学上无定义。此时界面显示"不可计算（缺少对照）"
   并改由贝叶斯统计判定，而不是显示一个空白格让人读成"没事"。

**统计结果永远只是线索。** 每条命中都带 `needsReview`，并明确路由到信号评估流程
（SIG-DET / SIG-ASM）由医学人员判断；自动报告、说明书效应、 notoriety 与渠道偏倚
这些混杂因素，无法用一张列联表消除。界面不会提供"确认信号"这个按钮。

配套的**病例列表汇总**（`/api/signal/line-listing`）按 药品 → SOC → PT 汇总已编码
反应，可直接用于 PSUR 例数章节，并同时显示编码覆盖率——让读者知道自己看到的
数字缺了多少。

### 后台工作流进程（`src/daemon/monitor.js`）

| 能力 | 说明 |
|---|---|
| 定时扫描 | 默认每 5 分钟（`PV_MONITOR_INTERVAL`），覆盖 7 类规则（见下） |
| 独立进程 | 作为服务器的子进程运行，服务与时限追逐互不拖垮 |
| 幂等 | 重复扫描不产生重复任务、通知或审计条目；可随时重启 |
| 自动关闭 | 条件解除后自动关闭任务，**关闭动作本身也审计** |
| 升级 | 记录超期 30 天以上自动升级为 critical 并通知质量负责人 |
| 可归属 | 所有自动化写入标注为 `monitor` 系统 actor，**actor_id 为空**，一眼可分机器与人工 |

扫描的 7 类规则：① 工作流记录超期（整条记录到期 / 单个步骤到期，含义不同，
分开处理）；② CAPA 缺有效性检查（ICH Q10 §3.2.2 / GVP 第 13 条）；③ 设备校准与
维护超期（本构建中无 PV 角色持有此类权限，规则处于休眠状态）；④ PV 培训过期与
超期未完成；⑤ 文件定期审核超期；⑥ 条件已解除的任务自动关闭；⑦ 已读且超过
90 天的通知清理。

> **为什么这很重要：审计追踪的纪律。**
> 一个每周期都往审计追踪里写字的监视进程，会把账本淹在噪音里、毁掉它的证据价值。
> 所以这里的规则是**只审计状态变化，从不审计扫描动作**：任务创建一次、升级一次、
> 关闭一次，重复周期完全幂等。

### 合规内核（所有模块共用）

| 能力 | 实现 | 法规依据 |
|---|---|---|
| 审计追踪 | 只可追加，SHA-256 哈希链 + HMAC，密钥存于数据库之外 | 21 CFR Part 11.10(e)、EU GVP Module I |
| 防篡改 | SQLite 触发器拦截 UPDATE/DELETE；链校验定位到具体断点 | ALCOA+ |
| 电子签名 | **两个独立识别要素**：密码 + 动态口令/一次性挑战码（TTL 120 秒，一次性消费） | 21 CFR Part 11.200(a)(1)(i) |
| 签名要素 | 姓名、时间、含义（封闭枚举）、理由，并与记录永久关联 | 21 CFR Part 11.200(a)(2)-(3) |
| 权限控制 | 15 个角色、46 项权限，职责分离在服务端强制 | EU GVP Module I、ICH Q10 §3.2 |
| 会话控制 | 空闲超时（30 分钟）+ 会话绝对上限（12 小时）+ 失败锁定（5 次/15 分钟），并解释登出原因 | 21 CFR Part 11.10(d) |
| 修改理由 | 所有安全性记录变更强制填写理由（少于 3 字符拒绝） | 21 CFR Part 11.10(e) |
| 历史重建 | 任一记录的历史版本可从审计链单独重建 | ALCOA+ "Enduring/Available" |
| 断链冻结 | 审计链完整性校验失败时拒绝启动并给出事件处置指引 | 21 CFR Part 11.10(e) |

职责分离的三道门，全部在服务端：**路由权限**（每条 REST 路由声明所需权限）、
**步骤角色门**（步骤只接受其定义声明的角色）、**独立性门**
（`independentOfAuthor` 步骤拒绝记录作者本人；系统管理员不能作为安全性记录的
唯一批准人）。

## 四、值得注意的设计决策

**领域是数据，不是代码。** 12 类流程全部由 `seed/workflows/*.json` 驱动，加流程
只需加文件；`src/domain/workflow.js` 是全系统唯一的状态机。检查表同理。

**权限表必须是三态，不能是两态。** 「允许 / 不允许」会让界面与运行中的系统矛盾：
PV 质量负责人持有 `record.close`，但内核仍然拒绝他关闭自己写的记录。所以每个
单元格有第三种状态 **⚠ 有约束**，附原因与法规依据，取自 `src/domain/constraints.js`
中 **20 项代码强制**的约束。用户点开看到的就是服务端真正会做的事。

**职责写在图上，不放在悬浮提示里。** 工作流示意图的每个步骤下面直接列出负责
岗位和该岗位的职责文字；设计理念一行字在领域卡、领域页、工作流页反复出现——
因为它恰恰是要截图、打印、贴到会议室墙上的东西。

**时间线从 Day 0（四要素齐备之日）起算。** 报告时钟以**首次获知且可识别患者、
可识别报告者、怀疑药品、不良事件四项齐备之日**为 Day 0：严重 ADR 15 日内、
非严重 30 日内、死亡病例立即报告并 15 日内完成调查报告（81 号令第 21、22 条；
GVP 第 49 条）、境外严重 ADR 30 日内（第 33 条）、境外暂停销售/撤市 24 小时内
（第 35 条）。用"病例做完那天"当作起算日是**检查最高频缺陷**——系统在录入表单
里明确要求填 Day 0 而不是录入日/完成日，并由后台进程按截止日催办。**随访不得
延误首次报告**：先提交首次报告，再按获新信息之日的时限提交跟踪报告（GVP 第
42 条）；四要素缺失不能作为不登记或删除报告的理由，只能生成随访任务。

**因果评价必须记录依据，不是只给结论。** 医学评价员按 WHO-UMC 六级判定，表单
强制填写时间关系、停药/再激发、其他病因解释、初始报告人评价与**评价依据理由**；
报告者未评价时默认存在关联，初始报告人已评价的无确凿医学证据不得降级（GVP 第
45 条）。评价结论与理由必须一致，评价步骤为签名步骤。

**职责分离是代码强制的。** 录入员不能作医学判断、不能签署结案；因果评价
（`causality`）步骤声明 `independentOfAuthor`，拒绝记录作者本人执行（GVP Module I
质量体系）；CAPA 执行者不得自评有效性；偏差提出人不能自己关闭记录；
`system_admin` 账号被明确拒绝作为任何安全性记录的唯一批准人
（`rbac.canSign` → `ADMIN_CANNOT_APPROVE`）。QPPV / 医学评价员 / 数据录入员的
分离直接写进角色权限矩阵。

**演示用统一密码是明确标注的风险，不是被默许的做法。** 内置的 13 个演示身份共用
`PV-Demo-2026!`，界面上用醒目警示条说明这违反 21 CFR Part 11.300(a)「账号唯一、
不得共用」的要求，并指出真实部署必须为每人签发独立凭证。演示便利性被保留了，
但它没有被伪装成合规做法。

**内审员不得审计自己承担职责的领域。** 服务端强制（`inspections.createInspection`），
越界返回 `SELF_AUDIT_NOT_INDEPENDENT` 并说明补救方式（由其他内审员主导，或改由
PV 质量负责人以管理评审形式进行）。**被拒绝的尝试本身也写入审计追踪**——一次
未遂的自审是关于质量体系的发现，即使什么都没改变。

**外部检查员的访问是限时的、只读的，且到期后自动失效。** `users.access_expires_at`
在**登录时和每个请求**都校验；到期账号自动标记为 `expired` 并记录原因；检查员的
**每一次查看行为本身也被记录**（`auditor_external` 只有读权限）。

**导出审计追踪本身是一条记录。** 每次导出都记录：谁导出的、多少条离开、导出时
用的过滤条件——写入发生在生成负载**之前**，因此生成后传输中断的导出依然留痕。

**可见性按职能关系判定，不按行政级别。** 曾设想把岗位分成 1/2 级、高级别可看低
级别的一切——**这个设计被否决了**，因为它与 PV 的组织方式相反：QA/内审之所以有
价值，恰恰因为它独立于处理流程。替代方案是 `src/domain/visibility.js` 的三档，
由**职能关系**决定：`cross_domain`（质量保证/内审/培训/检查员横跨全部领域）、
`own_area`（专职领域岗位看本领域）、`public`（其余只公开岗位名/职责/权限）。
**每一条拒绝都带理由**，由服务端随负载下发，前端只渲染判定结果、不做权限推断。

**领域限定的身份入口，由配置推导而非手工维护。** 只按领域的**专属流程**判断，
再加一份**显式声明**的贯穿性职能（QA、内审、培训、外部检查员）；刻意不用启发式
推导（曾试过按"出现在跨领域流程里的岗位"推导，结果把横向职能污染成了每个领域
都有几十个岗位）。

**自查判定"存在缺陷"必须填客观证据。** 判定为"部分符合"或"存在缺陷"时，必须
提供至少 10 个字的客观证据。无证据的负面判定在检查中不可辩护，所以直接在入口
拦住。

**配置库保持为可编辑 JSON。** 工作流与检查表定义不打进可执行文件，因为站点需要
能在不重新构建的情况下新增 PV 流程或调整流程。代价是 exe 需要同级 `app`/`seed`
目录。

★ = 核心模块

> ⚠️ **`.bat` 文件必须保持纯 ASCII，不要加中文。**
>
> `cmd.exe` 按控制台**当前代码页**逐字节读取批处理文件。两种失败方式：
>
> 1. 文件含 GBK 中文，但控制台被切到 UTF-8（`chcp 65001`）→ cmd 的读取偏移
>    中途错乱，开始执行注释和字符串的碎片，屏幕刷出一片
>    `'xxx' is not recognized as an internal or external command`。
> 2. 文件含 UTF-8 中文，但控制台停留在代码页 936 → 中文显示为乱码。
>
> 纯 ASCII 在 GBK、UTF-8 和所有旧代码页下**字节完全相同**，因此天然免疫任何代码页。
> 所以启动器可以安全地先执行 `chcp 65001`，让 Node 进程以 UTF-8 输出中文
> （与网页界面编码一致）。
>
> **所以：所有面向用户的中文都写在 `src/server.js` 的启动横幅里，不写在 `.bat` 里。**
> 修改批处理时请确认文件仍为纯 ASCII + CRLF。网页与 `src/` 则一律使用 UTF-8，
> 两者互不影响。

## 六、数据与备份

**所有数据都在 `data/` 目录：**

| 文件 | 内容 |
|---|---|
| `pv.db` | 业务数据与审计追踪（SQLite，WAL 模式） |

> 密钥丢失或与数据库不匹配，审计追踪将**永远无法校验**，且无法修复。

```bat
node scripts\backup.js                        :: 备份（VACUUM INTO 一致性副本 + 密钥 + 配置 + 清单）
node scripts\backup.js --label pre-upgrade    :: 带标签
node scripts\backup.js --verify-only <manifest.json>   :: 恢复演练
node scripts\verify-audit.js                  :: 校验审计链
node scripts\verify-audit.js --seal "飞检前封印"       :: 生成完整性封印
```

`--verify-only` 会做**完整的恢复演练**：先校验字节完整性（在打开文件之前），再
打开备份副本验证哈希链。这个顺序是刻意的——SQLite 仅打开文件就会重写文件头，
先打开再算哈希必然不匹配。

生产环境请每日自动备份，并定期执行恢复演练，留存记录（21 CFR Part 11.10(c)、
EU GVP Module I 质量体系 / Annex 11 §7.2 的要求）。

## 八、自检

跑全部 10 个套件：

```bat
node test\run-all.js
```

`npm test` 等价。之所以把 `node` 形式写在前面：Windows 默认的 PowerShell 执行

```bat
node test\run-all.js pv-engine e2e explorer
```

### 桌面启动器自检与故障自愈

`LeebertyPV.exe --selftest` 会无界面验证：发现 Node 运行时 → 定位服务入口 →
启动隐藏服务器 → 等待健康应答 → **原生窗口冒烟渲染全部核心视图并做布局质检**
（无退化控件、无越界）→ 停止并释放端口。这是发行前的启动器完整性证明。

如果服务器未能就绪（典型原因：`data\` 文件夹与 `audit-chain.key` 不一致，导致
审计追踪完整性校验失败），启动器会在约 22 秒后**弹出说明窗口**并直接提供
「重置演示实例」一键修复：损坏的 `data` 文件夹被**移到 `data-corrupt-<时间戳>`
保留现场**（绝不直接删除），随后生成一套全新演示数据——不会再有"窗口空白、
无从下手"的情况。无界面等价命令：

```bat
LeebertyPV.exe --repair-demo
```

> 生产实例请勿使用恢复功能：请按数据完整性事件处置程序处理并保全数据。

单独跑某一个套件：

```bat
node test\pv-engine.js    :: 报告时限阶梯、MedDRA 编码、比例失衡统计与检测 ★
node test\e2e.js           :: 核心引擎、签名、权限门、审计链
node test\monitor.js       :: 后台进程扫描规则与幂等性
node test\inbox.js         :: 待办聚合与动作分类
node test\explorer.js      :: 领域工作流视图、三态权限矩阵、参与者管理
node test\firstrun.js      :: 首次启动自动初始化与幂等性（空目录 → 可用实例）
node test\audit-roles.js   :: 可见性模型、内审员独立性、外部检查员限时与导出留痕
node test\assets.js        :: 浏览器 DOM、责任级联、受限名片、CSS 类完整性
node test\identity-flow.js :: 身份优先的启动流程、密码校验、各身份的落点
node test\operations.js    :: 操作执行、操作工待办、新增用户与账号生命周期
```

`pv-engine.js` 单独用临时库运行，不触碰实例自身的安全性记录。它钉住三类
**不会自己报错**的规则：时限是否从首次获知日而非录入日起算、统计量是否与
手算值一致、以及信号检测**是否真的会触发**——一个只会返回"无异常"的引擎，
同样能通过一个只检查它不崩溃的测试，所以套件里同时构造了真信号与平对照组：
既要证明能报出来，也要证明不会误报。

`run-all.js` 会按套件聚合退出码并**剥离继承来的 `GXP_*` 环境变量**（保留
`GXP_EDGE`）：多数套件不设任何环境变量、直接继承 shell，本机导出的
`GXP_DB_FILE` 会让套件偏离它自己的临时数据库并在 200 毫秒内失败且不给出有用
信息。`explorer.js`、`assets.js` 与 `identity-flow.js` 会启动真实服务器与真实
浏览器（Edge headless，通过 CDP）验证界面，因此也覆盖「视图文件已定义但未被
index.html 引用」这类不会抛错、只会导致白屏的问题。没有安装 Edge 时，这些套件
会打印 `skipped` 而不是失败。

`audit-roles.js` 测试的是**不会自己报错的规则**：可见性判定漂移了，界面看起来
照常工作；自我审计限制停止生效了，只表现为一次被允许的检查；到期校验失效了，
只表现为一次正常的登录。这三者破坏时都不产生任何异常，所以每条都用真实调用
断言。其中一项还**断言了边界本身**：外部检查员不能重算审计哈希链
（`audit.verify` 不授予）。

```bat
node scripts\verify-audit.js --record AES-2026-0001   :: 单条记录版本历史
node scripts\verify-audit.js --seal "飞检前封印"       :: 生成完整性封印
node scripts\audit-coverage.js                        :: 各 PV 领域内容覆盖审计
node scripts\screenshot-explorer.js                   :: 真实浏览器截图（需先启动服务）
```

### 9.1 定位：技术演示与参考实现，不是经过验证的系统

**本项目是技术演示与参考实现，用于说明一套药物警戒工作台可以怎样设计。**
它**没有经过软件验证**（GAMP 5），没有 URS、没有 IQ/OQ/PQ 方案、没有需求-测试
可追溯矩阵、没有验证总结报告。

这一点必须说清楚，因为后果是具体的：**用于产生或保存药物警戒记录的计算机化
系统，其自身必须先经过验证。** 用未经验证的软件产生受监管的安全性记录，本身
就是一条缺陷/偏差。所以本项目**不得**直接部署到受监管的生产体系中。要那样用，
需要先按你自己的质量体系完成验证——`seed/` 下的配置库可以复用，验证工作不能省。

**MIT 许可证授予的是著作权意义上的使用许可，不是适用性声明，也不是合规声明。**

### 9.2 演示数据是虚构的

演示数据集中的企业（`华东制药（演示）`）、人员姓名、病例与信号内容全部虚构，
仅用于展示工作流。**不包含任何真实企业的数据。** 首次启动生成演示数据需要显式
开启内置账号（`PV_BUILTIN_ACCOUNTS=1`），默认关闭时不会写入任何虚构记录。

### 9.3 内置账号共用密码是已标注的风险

演示实例的所有身份共用同一个密码（13 个内置演示身份 + 13 个演示数据集账号），这**违反 21 CFR Part 11.300(a)**「账号唯一、
不得共用」的要求，界面上以醒目警示条说明。真实部署必须为每个用户签发独立凭证。

双要素签名（§11.200）**默认已开启**：签名需要密码 + 一次性挑战码两个独立识别
要素。只有在本机演示、需要减少操作步骤时才用 `PV_SIG_2FA=0` 关闭——关掉它就
不再满足 §11.200(a)(1)(i)，界面的合规态势页会如实标记为「未满足」。
