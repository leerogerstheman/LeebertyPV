# 验证指南 · Validation Guide（LeebertyPV）

**本文档不是验证文件本身，而是编写验证文件时的输入清单。**

系统提供的是**证据与就绪度输入**；IQ/OQ 的签署、职责的指定、最终符合性判定，
仍须由站点具备资质的人员完成。

> ⚠️ 本软件按"现状"提供。投入药物警戒（PV）使用前，必须按贵司的计算机化系统
> 验证程序完成评估。未经验证即用于 PV 安全性记录，责任由使用方承担。

---

## 一、本系统的验证优势（请如实陈述，不要夸大）

| 特征 | 对验证的影响 |
|---|---|
| **零第三方运行时依赖** | 供应商评估范围极小——无需逐个评估 npm 包及其传递依赖 |
| **无构建步骤** | 交付物即源代码；不存在"源码与运行版本不一致"的风险 |
| **单文件数据存储** | 备份、归档、恢复的对象明确；无数据库服务需单独验证 |
| **配置与代码分离** | 新增流程/检查表无需重新验证代码，只需评估配置变更 |
| **自带合规态势核对** | 监管要求逐条给出**当前实际证据**，可直接摘入验证报告 |
| **演示身份与生产分离** | `PV_BUILTIN_ACCOUNTS` 关闭时实例不含任何虚构账号与记录 |

**同时必须如实说明的局限：**
- 系统未经过第三方认证或独立审计
- 就绪度评分是排序工具，不是法规符合性判定
- 单实例架构，无高可用与多站点同步
- 依赖操作系统文件权限保护数据文件
- `seed/checklists/` 当前未预置检查表模板，若启用自查需站点先放入并核实条款号

## 二、建议的验证范围（基于风险，GAMP 5）

按 GAMP 5 软件分类，本系统属于**类别 5（自定义应用）**，但风险等级取决于用途：

| 用途 | 建议风险等级 | 验证深度 |
|---|---|---|
| 仅用于流程参考与就绪度跟踪（不作为 PV 原始记录） | 低 | URS + 安装确认 + 权限确认 |
| 用于 ICSR/信号/PSUR/RMP/偏差/CAPA 记录（**作为 PV 记录**） | 高 | 完整 URS/IQ/OQ + 审计追踪确认 + 报告时限控制确认 + 备份恢复演练 |
| 作为给监管机构递交数据的**唯一数据源** | 高（需额外评估） | 上述全部 + 递交接口评估 + 更严格的数据完整性测试 |

**若作为 PV 原始记录**，必须额外确认：
1. 审计追踪在真实使用场景下的完整性（不只是测试环境）
2. 电子签名与人员身份的绑定关系（账号发放程序）
3. **报告时限起算逻辑**（Day 0 即首次获知且四要素齐备之日，非录入日）
4. 记录保存期限（建议与本品种注册要求一致，如注销后 10 年）与归档程序
5. 停机期间的纸质记录程序与事后补录规则

## 三、用户需求说明（URS）要点

建议 URS 至少覆盖以下条目，每条都应可测试：

### 功能需求
- FR-01 系统应支持个例安全性报告（ICSR）快速/常规流程，含接收登记、四要素核验、
  分类与时限判定、MedDRA 编码、因果评价、医学审核、递交、随访、结案
- FR-02 系统应支持信号检测与评估、PSUR/PBRER 编制、RMP 全生命周期、文献监测、
  AEFI 快速处置、投诉与召回联动、PV 偏差/CAPA/变更控制，共 12 类流程
- FR-03 系统应能根据流程定义自动生成步骤清单，并按角色与顺序控制执行
- FR-04 指定步骤（评价、审核、批准、结案等）应强制电子签名后方可完成
- FR-05 系统应支持受控文件的版本、审批、定期审核与阅知确认
- FR-06 系统应提供法规检查表，支持逐条判定与客观证据记录
- FR-07 检查发现的缺陷应能转为受控的 CAPA 记录并保持关联
- FR-08 系统应维护人员培训资质矩阵，并回答"某人能否执行某 PV 操作"
- FR-09 系统应能导出审计追踪、检查结论与安全性记录清单

### 合规需求
- CR-01 审计追踪应只可追加，任何修改或删除尝试应被阻止并记录
- CR-02 审计追踪应能证明未被篡改（完整性校验，定位到断点）
- CR-03 电子签名应使用至少两个不同的识别要素（密码 + TOTP/一次性挑战码）
- CR-04 签名应包含签署人姓名、日期时间、含义与理由，并与记录永久关联
- CR-05 每个用户应有唯一账号，不得共用（演示共用密码须被揭示为风险）
- CR-06 权限应按角色分配，职责分离（录入员不作医学判断；评价/审核/结案独立；
  QPPV / 医学评价员 / 数据录入员分离；系统管理员不作唯一批准人）
- CR-07 所有安全性记录变更应强制填写理由
- CR-08 会话应在空闲后超时，并告知用户登出原因
- CR-09 数据应可备份与恢复，恢复应可验证
- CR-10 记录的历史版本应可从审计追踪重建
- CR-11 **报告时限应从 Day 0（首次获知且四要素齐备之日）起算**，严重 ADR 15 日内、
  非严重 30 日内、死亡立即报告并 15 日内完成调查、境外严重 30 日、境外撤市 24 小时
- CR-12 超时限记录应生成受控待办并可追溯处置（偏差说明/升级）

### 非功能需求
- NFR-01 系统应在无互联网连接的环境运行
- NFR-02 系统不应要求管理员权限安装
- NFR-03 界面应支持中文与英文切换
- NFR-04 系统应能在 Windows 10/11 上运行
- NFR-05 系统应为单实例本地部署，数据文件位于 `data/`

### D. 工作流与时限控制

> **验证重点：时限的起算点。** 这是药物警戒系统里最容易被"看起来正常"掩盖的
> 缺陷——界面不报错、流程能走完，但审计追踪会把已超期的报告记成合规。因此下面
> OQ-D2 至 OQ-D5 四条不是重复检查"有没有截止日"，而是检查**截止日从哪里来**。

## 六、供应商评估说明

**本系统零第三方运行时依赖**（`package.json` 的 `dependencies` 为空），因此：

1. **供应商/构件评估范围极小**：无需逐个评估 npm 包，无需审查传递依赖的漏洞与
   许可；评估对象仅为系统本身与运行时（Node.js、Windows 内置的 .NET Framework）。
2. **需记录的运行时版本**：`node --version`、OS 版本、（可选）.NET Framework 版本。
3. **变更控制**：系统变更 = 代码/配置变更，走站点计算机化系统变更流程；
   `seed/` 下的流程与检查表 JSON 是配置变更的常见对象，应纳入配置管理
   （版本控制 + 变更记录）。
4. 桌面启动器由 Windows 自带 `csc.exe` 现场编译，无 NuGet、无第三方引用，
   可在评估中注明。

## 七、周期性回顾（GAMP 5 / Annex 11 §3）

建议**每年**进行一次系统周期性回顾，输入应包括：

1. **变更历史** —— 配置库变更（`seed/` 下 JSON 的变更记录）
2. **事件记录** —— 审计追踪中的 `system_error` 与 `access_denied` 条目
3. **权限复核** —— 用户清单、角色分配、离职账号处置（GVP Module I / ICH Q10）
4. **审计链完整性** —— 年度的完整性校验结果与封印记录
5. **备份与恢复** —— 恢复演练记录
6. **法规变化适应性** —— 新增/修订的法规条款是否已加入检查表库
   （注意：当前发行版未预置检查表，站点应建立自己的检查表并维护条款号）
7. **合规态势** —— 「合规态势」页面的当前证据与不符项
8. **时限合规回顾** —— 本年度快速报告 15/30 日合规率、超时偏差记录

回顾报告应形成文件并经 QA 批准。

## 九、已知局限（必须写入验证报告）

诚实陈述局限，比声称"完全符合"更经得起检查：

1. 本系统**未经过第三方认证或独立审计**
2. 就绪度评分与检查表是**辅助工具**，不构成法规符合性判定
3. 电子签名第二要素为 TOTP 或服务端挑战码，**不含生物特征**
4. 数据库文件**未做文件级加密**，依赖操作系统权限与磁盘加密
5. 单实例架构，**无高可用集群与多站点同步**
6. 检查表库当前**未预置模板**；站点自建检查表时**条款号必须对照法规原文核实**
7. 系统**不替代国家监测系统的传输通道**，E2B 回执在系统内留痕
8. 打印输出为浏览器打印样式，**正式核证副本程序需站点另行规定**
